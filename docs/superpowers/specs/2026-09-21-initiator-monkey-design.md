# 邀请者模式（主C猴子）—— 设计文档

日期：2026-09-21
状态：待用户评审
前置事实：[游戏规则知识库](../../game-rules.md)（合成结果类型随机、变身规则、棋盘对称等均以该文档为准）

## 1. 背景与目标

新增「邀请者」玩法：猴子号作为邀请者（initiator）发起合作，邀请高等级玩家帮打，自己承担辅助位——棋盘养天使+雪姬、技能全选辅助向。与现有「抢合作当帮助者（helper）+ 主C强袭」并存，两套打法互不影响。

- `run --main-c monkey --invite` 一条命令进入邀请者模式；不带 `--invite` 时现有行为零变化。
- 局内决策差异收敛在 `CultivationStrategy` + `MainCProfile`（现有框架的参数化扩展）；组队差异是新状态机分支（发起→等待→过滤→开局）。
- 交付方式：一次全做（用户定案 2026-09-21）。

## 3. 方案比选（已定）

- **策略层：扩展 `CultivationStrategy`（采用）**。猴子决策点与强袭同构（门禁/合成/变身），差异全部可用档案开关表达；`build_strategy` 的 `strategy` 字段继续保留作结构性差异的扩展点，本设计不动。
- 组队层：状态机内加 `INVITE_*` 状态（与 `FIND_COOP` 平级）。`CoopGrabCoordinator` 双线程是为「抢」设计的，邀请是等人，单线程轮询即可。

## 4. 配置设计

### 4.1 `MainCProfile` 新增字段（均有默认值，强袭行为不变）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `target_star_level` | int | 0=回退 run 级 | 主C门禁星级档案化（强袭 3 / 猴子 1） |
| `opening_summons` | int | 0=回退 run 级 | 开局召唤次数（强袭 7 / 猴子 5） |
| `forbid_star3_merge` | bool | false | 3 星软避让：过滤产物为 3 星的合并 |
| `hero_keep_counts` | dict[str,int] | {} | 各英雄保留数（monkey 档案：angel 1 / snow 1 / death_knight 0；主C隐含 1） |
| `required_lineup_heroes` | list[str] | [] | 阵容门禁：全部在场（≥1 个）才转技能 |
| `transform_sacrifice_order` | list[str] | [] | 变身牺牲顺序（受保留数约束）；空 = 用现有碰主C模式 |


## 5. 策略层设计（`tasks/strategy.py`）

### 5.1 门禁 `main_c_ready`

扩展为：主C星级达标（档案 `target_star_level`，猴子 1）**且** `required_lineup_heroes` 每类在场 ≥1。强袭不配该字段，行为不变。

### 5.2 合成决策（`select_merge` / `select_merge_batch` / 金币等待合成）

统一过滤，两个规则叠加：

1. **3 星避让**（`forbid_star3_merge`）：产物星级 = max(输入星级)+1 ≥ 3 的候选一律不选（含通配对）。强袭的「棋盘占满被迫合并」兜底对猴子**不生效**。
2. **保留数**（`hero_keep_counts`）：候选两输入类型各自的「在场数 − 本候选消耗数」≥ 保留数才可选。通配（幻天使）对中非幻天使一侧同样受保护；幻天使哲学沿用（有空位先召唤不花、占满才用）。

### 5.3 变身决策（`select_transform`）

档案 `transform_sacrifice_order` 非空时启用碰辅助模式：

- 触发：阵容不齐（`required_lineup_heroes` 有缺）且棋盘满且无安全合成候选（「卡住」）；
- **与金币门控的交互（2026-09-22 推演补充）**：现有召唤金币门控分支在「棋盘满 + 金币不足 + 无安全合成」时会循环等待金币恢复——但此时金币恢复也无法召唤（满盘），且**提前返回会吞掉变身出口**。猴子模式须在该分支中、返回等待之前先检查变身条件（阵容不齐且有可牺牲英雄），可变身则变身，否则落入干等；
- 牺牲：顺序取第一个满足「在场数 > 保留数」的英雄（死骑任意；雪姬需 ≥2；天使/猴子不在名单永不牺牲）；
- 连用：第一次未碰中对同一位置立即用第二次（沿用强袭逻辑，每局上限 2 次）。

### 5.4 召唤节奏（2026-09-22 用户确认最终版）

开局赠技能选完后：**首批召唤 5 个**（无金币门控，沿用强袭开局机制）→ **点击「准备完成」固定坐标 `opening_ready_done` (0.6802, 0.3017)**——固定规则，与阵容是否凑齐无关（动作后验证）→ 对局内进入凑阵容循环：

- 每批召唤 3 个（`summon_batch_size: 3`，金币门控沿用，不足等待恢复），每批后识别棋盘；
- 门禁满足（猴子≥1 + 天使≥1 + 雪姬≥1）即**停止召唤，转纯选技能阶段**；
- 棋盘满 → 安全合并腾格子（§5.2 滤网）继续召唤；无安全合并 → §5.3 变身碰辅助；变身耗尽仍不齐 → §5.5 干等（保持现状）到对局结束。

### 5.5 干等

变身耗尽且卡住 → 不合不召唤干等：重置无进展计数（不触发保守停止，同金币等待处理），INFO 日志记录卡住原因（缺哪类辅助、剩余可行动作），等对局自然结束进结算。

## 6. 组队状态机（`tasks/coop.py`）

`--invite` 时 `role=INITIATOR` 注入（局内棋盘自动走 `bottom_left_board`）。新状态与 `FIND_COOP` 平级：

```text
INVITE_CLICK:   前置：合作挑战页点【开始挑战】（复用现有按钮）进入邀请页面；
                5 步点击链（每步动作后验证：界面变化确认进入下一步）
                邀请按钮 → 一键邀请（弹窗层）→ 好友页签 → 公会招募 → 一键邀请（好友页）
INVITE_WAITING: 轮询 invite_text ROI（OCR「邀请」子串）：
                识别到   → 无人：等待超 reinvite_after_seconds（60s）无人进房
                           → 回 INVITE_CLICK 重走 4 步重发邀请；
                           连续空等重发超 max_empty_reinvites → 保守停止
                识别不到 → 复检一次防弹窗遮挡误判；确认有人进房后：
                  1. 点 invite_button 位置 → 弹出帮助者信息层
                  2. 读 helper_stage_progress（弹层内 ROI）→ 解析关卡数
                  3. 无论结果，点 close_button（× 模板匹配）关闭弹层
                  4. 分流：
                    ≥475  → INVITE_START
                    <475  → 点 invite_kick（请离）→ INVITE_COOLDOWN
                    读取失败 → 复检「邀请文字是否重现」（人已退则回本状态等待），
                              仍失败重试 N 次后保守停止（绝不盲踢/盲开局）
INVITE_START:   轮询开局按钮 ROI（invite_start_button_area）：
                「未准备」模板 → 帮助者未准备，继续等（超时策略见 §12）
                「已准备」模板 → 点击该按钮 → 开局，进局内培养
                邀请文字重现   → 帮助者退出 → 回 INVITE_WAITING
                                （新人可进重新过滤；超 60s 无人则重发邀请）
INVITE_COOLDOWN: 等 kick_cooldown_seconds → 回 INVITE_CLICK 重邀
```

结算返回**合作挑战页**（与强袭结算落点一致，结算/返回动作复用现有流程）后回 INVITE_CLICK（前置：点【开始挑战】），开下一局。

## 9. 错误处理与保守停止

- 踢人循环超 `max_consecutive_kicks` → 停止报警（匹配池可能整体低等级，等人工介入）；
- 单轮等待超 `wait_timeout_seconds` → 保守停止；
- 队友进度读取失败重试上限 → 保守停止；
- 邀请点击链任一步验证失败 → 重试 N 次 → 保守停止；
- 局内卡住干等不触发保守停止（§5.5），但日志可观察。
