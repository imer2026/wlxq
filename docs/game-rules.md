# 游戏规则知识库

本文档记录《永远的蔚蓝星球》中已经确认、并会影响自动化脚本判断和决策的游戏规则。这里只描述游戏事实，不约束具体代码实现。

## 游戏类型

游戏属于塔防游戏。每局游戏只能携带 4 种英雄，局内出现和合成产生的英雄都来自本局携带的这 4 种英雄。

## 主 C 选择

主 C 是本次自动对局重点培养和选择技能的英雄。当前比较流行、优先支持的主 C 有：

- 强袭，配置标识为 `assault`。
- 猴子，配置标识为 `monkey`。
- 天使，配置标识为 `angel`。
- 雪姬，配置标识为 `snow`。
- 死骑，配置标识为 `death_knight`。
- 狐狸，配置标识为 `fox`。

本次使用的主 C 在脚本启动时确定。最大合作局数、局内技能解锁前的最低召唤次数和目标星级从配置文件读取；启动参数只需要选择或覆盖主 C，不需要重复输入其余策略。合作模式已确认初始开放 7 个英雄格，必须累计召唤 5 次后才能使用局内「选择技能」。

## 金币与英雄召唤

游戏开始后，玩家需要消耗金币召唤英雄。每次召唤得到的英雄类型是随机的，但只会从本局携带的 4 种英雄中产生；新英雄的初始星级随机为 1 星或 2 星。召唤完成后，新英雄会出现在玩家自己的棋盘区域中。

召唤费用会随着本局召唤次数增加。脚本不需要提前计算完整的费用增长曲线，而应以当前金币、界面显示的召唤费用或召唤按钮是否可用为准。

脚本不能根据点击召唤按钮预测新英雄类型。一次召唤的最小判断流程为：

```text
识别当前金币、召唤费用或召唤按钮是否可用
→ 识别己方当前可用棋盘格
→ 点击召唤
→ 等待 1～2 秒，让召唤动画和英雄落位基本稳定
→ 重新识别己方棋盘
→ 找出新出现的英雄
→ 记录其类型、星级和位置
→ 更新棋盘状态
```

召唤成功必须通过棋盘变化确认，不能只根据金币减少或点击动作已经发出判断。新英雄必须重新识别，不能假设一定是 1 星，也不能根据召唤次数预测英雄类型。

## 金币与技能选择

召唤英雄和选择技能是完全独立的两个功能：

- 两者使用不同位置的按钮。
- 两者都需要消耗金币。
- 点击技能按钮后，每次出现 3 个随机候选技能。
- 候选技能不会重复，脚本需要从中选择主 C 的技能。
- 当前可从技能卡上的英雄图标判断候选是否属于主 C；同一主 C 的具体技能尚不能仅凭该图标区分。每张技能卡上的英雄图标即该技能所属英雄，识别到任一队友英雄的图标即可确认该卡不是主 C 技能（实机采集队友图标模板 2026-08-15）。

这里的「选择技能」指对局中点击「选择技能」按钮（消耗金币）刷新候选；进入游戏时的开局技能是免费自动弹出的（见下文「开局技能选择」），二者弹出的是同一个 3 张技能卡页面。

局内「选择技能」必须在本局累计召唤至少 5 次后才能使用。这个门禁不影响进入游戏时免费自动弹出的开局技能：开局技能仍应先处理完，再进入召唤阶段。

技能选择流程：

```text
确认当前策略允许选择技能
→ 到达配置的技能检查时间
→ 点击选技能按钮的通用 hotspot
→ 等待3个技能候选出现
→ 在候选区域识别主C英雄图标
→ 命中主C候选时随机选择其中一个
→ 连续多帧未命中时，将候选 ROI 横向三等分并随机点击一列中心
→ 点击后验证候选界面关闭或技能已经生效
```

召唤按钮和技能按钮必须使用独立的 Locator 和 ROI，不能因为两者都消耗金币而共用定位或状态判断。3 个候选中没有识别到主 C 图标时，从当前候选中随机选择 1 个，并照常验证选择成功。同一个主 C 图标模板如果在多个候选位置同时达到阈值，不把它判定为阻塞异常，而是从这些主 C 候选中随机选择一个。三张卡片在技能候选 ROI 内横向等距分布，兜底点由 `Locator` 取 ROI 宽度的 `1/6`、`3/6`、`5/6` 和高度中点计算，无需额外热点标定；ROI 缺失或无效时保守停止。

脚本不需要识别金币数量，也不需要为技能按钮采集可用/不可用两套模板。点击后在限定时间内没有出现候选技能时，本轮不继续点击候选，而是等待下一次检查。达到主 C 目标后的技能检查间隔前期约为 4.5～6 秒、后期约为 9～11 秒，具体值每次从配置区间中随机取得，用于适应动画和界面时序变化。

### 开局技能选择

进入游戏后，本局可能带有开局技能。开局技能是游戏**免费赠送**的：进入对局后技能选择页面会**自动弹出**（不需要点击「选择技能」按钮、也不消耗金币），页面给出 3 张技能卡，玩家从中选择即可。开局技能页面与对局中点击「选择技能」按钮（消耗金币）弹出的页面是同一个页面，都用 3 张技能卡 + 【选技能】图标识。

【选技能】图（`buttons/xuan_ze_ji_neng.png`）出现即表示当前处于技能选择页面（无论开局免费弹出还是局内花金币进入）。开局技能页面会**遮住召唤按钮**，因此必须先把技能选完、页面消失后才能召唤。

**天使开局技能是特例**（实机确认 2026-08-15）：天使英雄的开局技能页面**不出现【选技能】图**，也没有可匹配的主 C 技能图标，只出现专属的天使开局标识（`buttons/tian_shi_kai_ju.png`）。该页面同样给出 3 张技能卡，脚本无需识别具体技能，在 3 张卡中随机选一张即可。

开局技能的识别与选择流程：

- 进入游戏后按「先选技能、再召唤」识别开局类型：【选技能】或天使开局标识可见 → 处于技能选择页面（本局有开局技能）；【召唤】（`buttons/zhao_huan.png`）可见且无【选技能】→ 本局无开局技能，直接进入召唤。
- 【选技能】可见时：在技能 ROI 匹配主 C 技能图标（`skill_icon_templates`），随机点其一；图标在动会单帧漏检，连续多帧重试。
- 天使开局标识可见（无主 C 图标可匹配）→ 直接将技能候选 ROI 横向三等分，随机点击一张卡片的中心，无需等待识别帧。
- 连续 `skill_recognition_frames` 帧未识别到主 C 技能 → 将技能候选 ROI 横向三等分，随机点击一张卡片的中心。
- 每选一张后留在技能选择状态再次识别；**以“找不到【选技能】图”作为开局技能选完的判据**——此时【召唤】按钮出现，进入召唤阶段。

“以找不到【选技能】为完成判据”不表示无限等待；连续空识别和识别失败次数必须有明确上限。

## 条件驱动的召唤策略

是否继续召唤由具体任务提供的目标条件决定，而不是简单地持续消耗全部金币。脚本每次准备召唤或选择技能前，都应基于最新的棋盘识别结果重新计算策略。

当前目标是得到至少一个星级不低于 2 星的主 C。2 星、3 星或 4 星主 C 都满足星级条件；但只有“累计召唤至少 5 次”和“主 C 达到目标星级”同时成立，才能停止培养并进入局内技能选择。

合作模式的初始开放格数和技能解锁规则已经确认：

```text
initial_board_capacity = 7
minimum_summon_count_before_skills = 5
每累计召唤 5 次英雄，自动开放 1 个新格
```

因此第 5 次召唤完成后，局内技能选择解锁，棋盘也从 7 个开放格扩为 8 个开放格。

使用格子分类模型后，进入游戏并完成开局技能选择时，先识别一次完整棋盘作为基线。此后不再把前 7 次召唤作为一个批次，而是始终执行“召唤 1 次 → 等待 1～2 秒 → 多帧识别全部 12 格 → 决策下一步”。前 5 次属于强制召唤阶段：点击动作成功发送后立即累计召唤次数；即使该轮模型没有确认棋盘变化或提前识别到至少 2 星主 C，也继续逐次召唤到第 5 次，识别异常只记录日志，不能中断强制阶段。第一版策略建议强制阶段不插入合成，以最少动作先完成技能解锁门禁；这属于可调整策略，不是游戏规则。

```text
先识别完整棋盘作为基线
→ 召唤1次
→ 等待1～2秒
→ 连续识别多帧并更新当前棋盘；未确认变化也不阻断前5次召唤
→ 累计召唤次数不足5次：继续逐次召唤，不进入局内技能选择

累计召唤次数至少5次，且存在 hero_type = 主C、star_level >= 2 的英雄
→ 停止召唤
→ 停止合成
→ 后续选择技能

累计召唤次数至少5次，但仍没有达到目标星级的主C
→ 如果存在合法合成对，则执行合成
→ 每次合成后重新识别并检查目标；出现2星、3星或4星主C都立即停止
→ 如果没有合法合成对，则只召唤1个新英雄
→ 等待1～2秒后重新识别和检查
→ 重复直到达成目标
```

技能解锁前的最低召唤次数、召唤后识别等待区间、主 C 英雄、目标星级以及条件满足后的行为都属于任务配置，不应写死在通用召唤逻辑中。合法合成对只要求英雄类型相同且星级相同，不排除 1 星主 C。多个合法合成对同时存在时，当前最简单的策略是优先合成非主 C；更详细的排序规则后续补充。主 C 判断和合成必须使用可用于决策的最新 `BoardSnapshot`。前 5 次强制召唤以点击成功发送计数；第 5 次以后的追加召唤和所有合成仍需要后续棋盘变化验证。

如果没有合法合成对，则在金币、召唤按钮和可用棋盘格允许时继续召唤；条件暂时不满足时等待并重试，而不是执行错误合成。

## 棋盘与合作模式

召唤出的英雄位于类似棋盘的区域中，英雄的识别、合成和位置跟踪都应限制在当前玩家自己的棋盘 ROI 内。合作模式初始开放 7 个英雄格，每累计召唤 5 次自动开放 1 个新格。

合作模式中有两名玩家，双方区域位于画面下方：

- 发起合作的玩家位于左下方，角色记为 `initiator`。
- 帮助合作的玩家位于右下方，角色记为 `helper`。

本脚本的主要工作流是寻找其他玩家发起的合作请求并抢先加入，因此正常进入战斗后角色为 `helper`，己方棋盘位于右下方。首次进入招募前必须先正向识别当前画面为游戏首页；未识别为首页时立即报错，不发送任何输入。确认首页后依次点击首页聊天、招募、打开难度弹窗、按配置选择难度、关闭难度弹窗；一局结束点击返回后，直接点击合作页面聊天即可再次开始抢合作。上述顺序是固定业务流程，由任务代码编排；通用点击位置以 9:16 游戏客户区比例坐标保存在 `configs/tasks.yaml`。抢合作不识别“加入”按钮，而是在招募页循环点击配置位置，每点击一批后检查准备按钮。出现准备按钮即表示已经抢到合作，脚本点击准备按钮后等待对局界面稳定。该等待过程不是单独的游戏状态。

难度选择面板的关闭方式随游戏更新变更（实机确认 2026-08-17：用户手动验证 + 自动流程完整跑通）：旧版点击弹窗左下「取消」按钮；更新后「取消」按钮不存在，面板打开时左侧栏「招募」按钮仍可见，点击它收起面板（关闭坐标与进入招募的 `open_recruit` 相同）。

合作只能通过玩家自己点击「加入」进入，游戏不会主动把玩家拉进对局（实机确认 2026-08-17）。因此准备按钮只会在发出加入点击之后出现，招募入口的各子步骤（首页确认/聊天/招募/开面板/勾难度/关面板）不可能出现准备、返回、击杀奖励弹窗、选技能、召唤中的任何一个。界面标志据此按状态门控识别：入口子步骤不查任何全局标志，抢合作（JOIN）只查准备按钮，对局内各状态查各自随机出现的标志。

实机确认（2026-08-15）：发起者可以把已加入的玩家踢出合作。被踢后对局不会开始，玩家回到游戏首页。已勾选的难度在本会话内保持选中，再次点击同一难度会取消勾选，因此被踢后重新进入招募不应重复勾选难度。

组队大厅（已抢到合作、已点准备、对局未开始的等待画面）左下有【退队】按钮。房主可能长时间不点开始；此时点【退队】可退出本队，随后重新抢其他合作。

战斗界面的按钮外观会随**城墙皮肤**变化（实机确认 2026-08-16）：切换城墙皮肤后【召唤】按钮的样式与默认皮肤截图的模板（`buttons/zhao_huan.png`）不匹配，导致开局后长时间识别不到召唤按钮。使用非默认城墙皮肤时需要对战斗界面按钮重新采集模板，或切回默认皮肤。

合作难度列表分两个分区（实机确认 2026-08-19）：普通难度「合作模式-第1层」～「合作模式-第12层」，其后紧接彩虹难度「合作模式-彩虹1层」～「合作模式-彩虹19层」（第12层的下一行就是彩虹1层）。难度面板每次打开，列表都定位在普通难度区顶部（第1层可见）；彩虹行在列表更深处，必须从下往上拖动（列表内容上移）滚入彩虹区后才能勾选。当前脚本只打彩虹难度：`coop_difficulties` 配置和命令行参数中的编号一律指彩虹难度，`1-10` 表示勾选彩虹1→彩虹10，程序统一**从小到大**依次点击——面板打开停在列表顶部、编号小的先出现，顺着向下滚动单程点完，无需回滚。彩虹文字模板目前采集到 `cai_hong_1`～`cai_hong_18`，彩虹19 尚无模板。列表每屏随滚动位置显示 4 或 5 行；识别采用**逐模板独立匹配**——每个编号一张实机裁剪的文字模板，各匹配各的，不做序列推断（2026-08-19 实机定案）；相似编号命中同一行时按中心点距离合并、保留置信度最高者。滚动通过两个比例 hotspot 形成的固定比例拖动手势完成，因此实际像素距离随游戏客户区尺寸变化。

难度文字模板不包含右侧复选框；点击后复选框变为选中状态，文字模板仍可正常识别。勾选框状态**不参与**自动化决策（2026-08-19 实机定案的开环设计）：识别难度文字 → 点击文字中心 → 推进，点击发送即计为已选。原因：系统会推送合作邀请、帮打宠物邀请等弹窗（实机观察 2026-08-19：位置固定、高度约一行、持续约 5~15 秒、经常连续出现、可能并排多个），弹窗只遮挡行右侧的勾选框、**从不遮挡行文字**——闭环识别勾选框会在遮挡期产生两种反向失败（已勾选的被再次点击而取消勾选 / 未勾选的被误判已选而漏选，两者实机都发生过），且邀请类型将来还可能新增。开环的代价：已选过难度的会话必须用 `--skip-difficulty-selection` 跳过选择步骤，再次点击已选难度会取消勾选。勾选框模板（`gou_xuan`=选中绿勾、`gou_xuan_kong`=空框）已实机采集，留档备查未使用。滚动后读取下一帧并重新识别；识别为空表示列表还在普通难度区，继续向更大难度滚动；可见集合未变化或达到滚动上限时，记录并跳过当前目标难度，继续后续合作流程。

脚本启动合作任务时必须先确定当前玩家角色，再选择对应的棋盘 ROI：

```text
co-op + initiator → bottom_left_board
co-op + helper    → bottom_right_board
```

棋盘 ROI 应通过对应分辨率的配置或首次校准得到，不能在任务代码中写死屏幕绝对坐标。脚本只能在己方棋盘中查找召唤结果和执行合成，不能因为另一方棋盘出现相似英雄而误操作。

棋盘 ROI 表示己方棋盘可能占用的整体区域。英雄识别应覆盖完整棋盘 ROI；程序不需要在视觉上区分未开放格和已开放空格，识别到英雄即表示对应位置已占用。固定格位坐标用于归属英雄位置以及计算合成拖动的起止点，不用于判断格子是否已经开放。是否能够继续召唤以召唤按钮状态为准，召唤成功仍以动作后棋盘中的英雄变化为准。

棋盘呈锯齿形布局，每个棋盘共 6 排 14 格，使用方形格子、不交错排列，排 1 位于顶部：

- 排 1：1 格，靠棋盘外侧（远离中间分隔线一侧）。
- 排 2-3：各 2 格，靠外侧连续排列，靠近中间分隔线一侧的列为空。
- 排 4-6：各 3 格，满列。

左右棋盘沿中间分隔线镜像。以左棋盘为例，列从外到中间编号 A/B/C：排 1=A、排 2-3=A+B、排 4-6=A+B+C；右棋盘镜像对应 A'/B'/C'。格子等大、间距固定，知道一个格子尺寸和棋盘锚点位置即可推导全部 14 格的中心坐标，无需逐格采集。排 6 的 A 列和 C 列（6A、6C）是宠物位置，不会出现英雄；英雄识别时应跳过这两格，只对其余 12 格做模板匹配，坐标模型仍计算全部 14 格位置，识别时按格子类型过滤。其他游戏模式的布局仍待补充。

## 英雄属性

脚本关注棋盘上英雄的三个基本属性：

- `hero_type`：英雄类型，即具体是哪一个英雄。
- `star_level`：英雄星级，取值为 1、2、3、4。
- `position`：英雄当前在棋盘中的位置。

英雄在游戏画面中是动态的，可能改变朝向和动作。同一个英雄至少需要使用朝左、朝右两张模板定位；必要时再增加待机、移动或攻击动作模板。

### 星级的视觉呈现（实测确认，2026-08-14）

星级直接体现在棋盘格画面的英雄形象数量上，这是人工标注和分类器训练时判断星级的依据：

```text
1 星 = 该英雄的 1 个单独形象
2 星 = 该英雄的 2 个并列形象
3 星 = 该英雄的 3 个并列形象
4 星 = 不是 4 个形象，而是一个放大版的单独形象（立绘可能与 1 星不同，但始终是 1 个）
```

并列形象的排布（实测确认，2026-08-14）：2 星是左右两个挨边并列；3 星是左右两个并列、第三个在上层露出（「左右上」布局）。对分类器的影响：1 星与 4 星都是「单个形象」，靠体型和立绘差异区分，是最易混淆的一对；2 星与 3 星因布局差异明显（挨边并列 vs 带上层），较易区分。训练数据必须覆盖每个英雄的全部 star1~star4。

## 英雄合成规则

只有英雄类型相同且星级相同的两个英雄才能合成。

星级提升规则：

```text
两个同种1星英雄 → 一个2星英雄
两个同种2星英雄 → 一个3星英雄
两个同种3星英雄 → 一个4星英雄
```

4 星是当前最高星级，不再参与合成。

合成操作通过拖动完成：把一个可合成英雄从起点拖到另一个英雄所在的终点。合成结果保留在终点位置，合成动画通常持续约 1～2 秒。拖动方向尽量**从下往上**（2026-08-16 实机规则）：起点取行号更大（更靠下）的英雄，例如 1A 和 4B 应从 4B 拖到 1A；同一排的两个格没有上下之分，按候选原顺序拖。

**两个 3 星合成 4 星时，系统弹出一次赠送的技能选择页**（实机确认 2026-08-16）：与常规技能选择同一个 3 选 1 界面，不花金币；页面会遮住整个棋盘导致棋盘识别为空。从中任选一张后页面关闭、棋盘恢复。补充实机确认（2026-08-21）：

- 页面主标识是【请选择1个额外技能】提示条（`skills/4_xing_e_wai_ji_neng.png`），该文案**只在赠送页出现**，只要不选技能页面就常驻（「恭喜获得满星」横幅同样常驻）；【选技能】图在该页**不稳定**，实机出现过整页等待选择却始终未命中的情况，因此赠送页判定以提示条为准。
- 页面可能被 Boss 奖励弹窗遮挡，先关闭弹窗即可识别到提示条。
- 对局结束时页面直接消失，无需也无法再选择，流程转入结算等待。

不同英雄不能合成；错误拖动不会产生合成结果。脚本不能仅根据拖动已经执行就更新棋盘，必须等待后重新识别。如果起点和终点英雄仍然存在，则视为合成失败。

## 合成结果随机规则

合成会消耗两个输入英雄并生成一个高一星英雄。新英雄的类型不继承输入英雄，而是从本局携带的 4 种英雄中随机产生。

假设本局携带英雄 A、B、C、D：

```text
A（1星）+ A（1星）
→ 随机得到 A、B、C、D 中的一个2星英雄
```

也可能出现：

```text
A（2星）+ A（2星）
→ C（3星）
```

因此合成前只能确定结果星级，不能提前确定结果英雄类型。

## 自动化判断要求

脚本在执行合成前需要识别：

- 棋盘上每个英雄的类型、星级和位置。
- 哪些英雄满足“同类型且同星级”的合成条件。
- 候选结果的识别置信度是否足够执行拖动操作。

一次合成的最小流程：

```text
识别当前棋盘
→ 找到同类型、同星级的一对英雄
→ 执行合成操作
→ 等待合成动画结束
→ 重新识别棋盘
→ 确认出现一个高一星英雄
→ 识别新英雄的实际类型和位置
→ 更新棋盘状态
```

合成成功不能仅通过输入动作是否发出判断。脚本必须重新截图，并验证：

- 两个输入英雄对应的棋盘状态已经改变。
- 出现了一个比输入英雄高一星的单位。
- 新英雄属于本局携带的 4 种英雄之一。
- 新英雄的类型、星级和位置能够被可靠识别。

如果合成后的英雄被动画或特效遮挡，应等待后重试识别；超过重试次数仍无法确认时，应记录截图并暂停，不能继续根据旧棋盘状态操作。

## 完整自动化范围

脚本负责从寻找合作到达到最大局数的完整流程：

完整的已确认执行顺序和流程图见 [自动化执行流程](automation-flow.md)。

```text
寻找其他玩家发起的合作
→ 首次正向识别游戏首页；不是首页则报错停止
→ 确认首页后依次点击首页聊天、招募，按从小到大选择配置难度并取消难度弹窗
→ 成批循环点击抢合作位置
→ 识别并点击准备按钮，以 helper 身份进入游戏
→ 识别右下方己方棋盘
→ 检查是否需要选择技能；需要则持续选择直到选完
→ 每次只召唤1个英雄，等待1～2秒后用多帧模型结果重新检查12格
→ 前5次强制逐次召唤；提前出现至少2星主C也要完成第5次召唤
→ 完成至少5次召唤后，未达成主C目标时优先合成非主C合法对
→ 无可合成对时再召唤1个英雄并重新检查
→ 已召唤至少5次且出现2星、3星或4星主C后停止召唤和合成，后续金币用于选择主C技能
→ 按随机时间间隔点击选技能按钮并选择主C技能
→ 识别到胜负页面共用的返回按钮，认定本局结束
→ 依次点击点赞、领取宝箱、返回；点赞和领取宝箱只发送一次点击，不验证结果
→ 返回按钮消失后累计已完成局数
→ 未达到 max_rounds 时点击合作页面聊天，打开再关闭难度弹窗刷新合作邀请，然后继续抢合作
→ 达到 max_rounds 后安全停止
```

`max_rounds` 是任务配置，用于限制本次连续帮助合作的最大局数。当前不区分胜利和失败：两种结算都会出现返回按钮，因此返回按钮是本局结束的统一标志。只有按“点赞 → 领取宝箱 → 返回”执行并确认返回按钮消失后，才更新 `RoundCounter`。断线暂不单独处理。除最大局数外，运行时还保留单次抢合作的最长时长上限（`find_coop_max_duration_seconds`），避免脚本无限循环。

结算画面有【双倍奖励】按钮（实机确认 2026-08-16）：若在结算弹出的瞬间点击落上去（如恰好同时在点技能），会弹出双倍奖励确认窗，挡住正常结算操作。确认窗有稳定标识（`buttons/shuang_bei.png`）和取消按钮（`buttons/qu_xiao_shuang_bei.png`），点击取消即回到正常结算。

## 最小业务概念

| 概念 | 含义 |
|------|------|
| `Lineup` | 本局携带的 4 种英雄 |
| `CoinState` | 当前金币、召唤费用以及召唤按钮是否可用 |
| `CoopRole` | 合作模式中的发起者或帮助者角色 |
| `BoardRegion` | 根据游戏模式和玩家角色确定的己方棋盘 ROI |
| `BoardCapacity` | 根据已确认的扩格规则或英雄数量得到的辅助统计；不要求通过视觉区分未开放格和空格 |
| `BoardHero` | 棋盘上一个英雄的类型、星级、位置和识别置信度 |
| `BoardSnapshot` | 某一识别时刻的完整棋盘状态 |
| `SummonResult` | 一次召唤后实际出现的英雄类型、星级和位置 |
| `DecisionPolicy` | 根据目标条件和最新棋盘状态决定继续召唤或切换到其他行为 |
| `SkillCandidate` | 一次技能选择中出现的候选技能及其识别置信度 |
| `SkillPriority` | 主 C 技能的有序选择优先级 |
| `MergeCandidate` | 满足同类型、同星级条件的一对英雄 |
| `MergeRule` | 两个同种同星英雄合成为高一星英雄的规则 |
| `MergeResult` | 合成后实际产生的英雄类型、星级和位置 |
| `RoundCounter` | 当前已完成局数和允许的最大局数 |

后续发现新的、会影响脚本决策的游戏规则时，应继续补充到本文档中。合作流程尚未确认的策略、配置值和截图资料统一记录在 [合作主流程 TODO](coop/TODO.md) 中；跨任务待办记录在 [项目 TODO](todo.md) 中。
