# 格子分类器数据采集与标注方案

本文档记录合作模式主 C 培养阶段的候选识别方案：从完整游戏客户区截图中自动裁取己方棋盘格，人工按英雄和星级分类，再训练本地轻量图像分类器。

实际采集、裁剪、标注、训练和评估命令见[英雄格分类器使用手册](hero-classifier-usage.md)。

该方案目前处于验证阶段，尚未替代现有模板匹配实现，也不得作为已经实机验证的能力。游戏规则仍以[游戏规则知识库](../game-rules.md)为准，当前自动化流程仍以[自动化执行流程](../automation-flow.md)为准。

> **12 格标定门禁已完成（2026-08-11）。** helper 棋盘使用排2～排6共 10 格实测中心拟合等距参数，并通过带裁剪框和格子标签的预览图对全部 12 格逐格人工确认；其中 1A、2A 由已确认的等距模型定位。该坐标已经确认可用于正式裁剪、标注和训练。

## 目标

- 原始素材只要求保存完整游戏客户区截图，标注者不手工裁格子。
- 程序根据己方角色、棋盘比例坐标和固定格位模型，自动裁出每张截图中的 12 个英雄格。
- 原始完整截图按局保存；选定多局后创建一个 split import，批内集中裁切、联合聚类，再由标注者把选中的图片移动到 split 共用的 `labeled/`。
- 分开标注“格子已开放但为空”和“该逻辑位置尚未开放”；两类都保留普通画面及被技能、弹道或其他特效覆盖的困难负样本。
- 标签仍然可靠的部分遮挡英雄直接按真实英雄和星级保留；英雄或星级无法确认的严重遮挡进入 `unknown`。第一版不额外区分 `clean/occluded`。
- 第一版保留所有裁剪结果、不删除任何素材；裁剪默认跨格按视觉状态自动聚类成簇子目录，仅作为标注便利（标注者从簇里挑代表移动），簇内未标注帧留在 `unclassified/`，训练只读 `labeled/`。
- 训练时按整局划分训练集、验证集和测试集，并通过采样控制类别和重复帧权重。
- 每次创建 import 前扫描所有历史 import；请求中已经完成裁切、聚类的来源局提示其原 split/import 并跳过，避免重复生成同一局素材。其余新局照常组成新 import；如果没有新局，则不创建空 import。

## 非目标

- 本方案不修改游戏文件、不注入游戏进程，也不读取或分析网络数据。
- 数据采集阶段不自动执行人工无法确认的英雄或星级标签。
- 第一版不训练大模型，不要求独立显卡，也不在正式运行环境安装完整训练工具链。
- 尚未实测前，不承诺一个分辨率训练的模型可以直接覆盖所有分辨率。

## 数据采集

### 输入

每局保存完整的游戏客户区截图。初始建议约每秒采集 1 张；实际间隔应作为采集配置，不写死在业务代码中。

以一局 6 分钟计算：

```text
6 × 60 = 360 张完整截图/局
360 × 12 = 4320 张原始格子裁剪图/局
```

`frame` 表示本局完整截图的顺序号，不表示视频编码中的帧序号。真实采集时间、窗口客户区尺寸、DPI、角色和来源截图路径应写入数据清单，不继续塞入裁剪文件名。

### 实时采集与异步落盘

实时阶段只截取完整游戏客户区，不执行 12 格裁剪、模板识别或模型推理。采集和保存分离：

```text
采集线程：按固定时间点每秒截取一次完整客户区 -> 放入有界保存队列
保存线程：从队列异步编码 PNG 并写入本局 raw 目录
局后处理：离线读取 raw 目录并裁出 12 个英雄格
```

采集间隔必须按本局开始时间计算固定目标时间点，不能在每次保存完成后简单 `sleep(1)`，否则截图和写盘耗时会不断累积。例如目标时间点应为 `0、1、2、...、359` 秒，而不是“本次处理结束后再等待 1 秒”。

保存队列必须设置明确上限。队列满、截图失败、窗口失效或 PNG 保存失败时记录原因和对应 `frame_index`，不得静默丢帧，也不得因为落盘持续变慢而无限占用内存。数据采集失败只影响本次素材完整性，不参与游戏任务决策。

一局结束后至少输出：

```text
理论采集数量
实际截图数量
成功保存数量
失败或丢弃数量及原因
截图耗时平均值/最大值
PNG 保存耗时平均值/最大值
保存队列最大长度
```

6 分钟每秒 1 张的 360 张是理论数量。实际数量可能因进入对局识别稍晚、结算提前、窗口短暂失效或单次处理超时略少；训练数据不要求强行补足到 360 张。如果实机无法稳定维持每秒 1 张，可以把间隔调整为 2 秒，一局仍可得到约 180 张完整截图和 2160 张格子图。

### 自动裁格

裁剪程序应复用 Locator 的棋盘格位模型：

1. 从完整游戏客户区截图和本局角色确定己方棋盘。
2. 根据客户区比例坐标换算格子中心和裁剪范围。
3. 只裁取 12 个英雄格，跳过宠物格等不会出现英雄的位置。
4. 裁剪结果保存为 PNG，不改写或删除原始完整截图。
5. 裁剪范围允许保留落入格子区域的技能、弹道和遮挡效果，不为得到“干净英雄图”而二次抠图。

不同显示器分辨率、客户区尺寸或角色的数据必须能够从上级目录和数据清单中追溯。显示器物理分辨率可沿用模板包标识；实际客户区尺寸和 DPI 单独写入清单。

裁剪在一局结束后离线执行，不阻塞实时截图和游戏流程。对于同一分辨率、客户区尺寸和角色，12 个格子的像素裁剪范围只计算一次；每张完整截图只读取和解码一次，随后连续裁出 12 个格子并保存为小 PNG。

以 360 张完整客户区截图、4320 张格子图为例，普通 SSD 和现代 CPU 上预计约需 30 秒至 2 分钟；机械硬盘、杀毒软件扫描大量小文件或较高 PNG 压缩等级可能增加到约 2～5 分钟。该数值只是容量规划参考，正式实现后必须在实际采集电脑上记录真实耗时。

离线裁剪可以使用少量并发工作单元，例如 4 个；应按一张来源截图作为一个处理单元，避免多个工作单元重复读取同一张完整截图。并发数量必须有限，防止 PNG 编码和大量小文件写入争用磁盘。优先使用较低 PNG 压缩等级换取更快处理速度，同时保持无损图像，不改用会引入压缩伪影的格式。

裁剪结束后至少输出：

```text
完整截图总数
理论格子图数量
成功裁剪数量
读取失败、尺寸不符和写入失败数量
总耗时
平均每张完整截图处理耗时
```

### 自动聚类的定位与用途

一局可能产生 3000～4000 多张格子图。让标注者逐张浏览这些散图，人工成本过高，因此同一 import 中的多局全部裁完后，把该批 `unclassified/` 中的全部格子图联合聚成若干簇目录。不同 split 不混合聚类。

自动聚类的唯一目的，是把大量相似画面放在一起，缩小人工查找范围：

```text
数千张散图 -> 若干相似画面簇 -> 人工打开簇目录挑选 -> 移入 labeled
```

自动聚类不是英雄分类器，也不是自动标注步骤：

- 聚类结果只保存在 `unclassified/`，不会自动写入英雄或星级标签。
- 训练器只读取人工确认后移入 `labeled/` 的图片，留在簇目录中的图片不参与训练。
- 一个簇只表示画面相似，不承诺簇内必然属于同一英雄、同一星级或同一种空格状态；标注者仍按实际画面挑选。
- 纯度较高的簇可以全选移动；混合簇可以只挑其中符合标签的图片，剩余图片继续留在 `unclassified/`。
- 聚类不删除、不覆盖裁剪图，只改变待标注图片的目录组织；原始完整截图也保持不变。

因此聚类阈值影响的是“人工挑图是否方便”，而不是训练标签的正确性。阈值偏低会产生更多小簇，阈值偏高会产生更多混合簇；两者都必须经过人工选择后才能进入训练集。

### candidates 候选图

一级聚类完成后，程序为每个一级簇生成少量候选图，使标注者日常只需浏览 `candidates/`：

```text
一级聚类：阈值35
├─ 一级簇 ≤ 100张：不二次细分，直接挑最多10张
└─ 一级簇 > 100张：阈值15二次细分，每个二级簇挑最多10张
```

每个最终组先选择排序稳定的第一张，再逐次选择与已选集合视觉差异最大的图片，以免候选名额被连续近似帧占满。候选图复制到 `candidates/<一级簇>/<二级簇>/`，不会移动或删除 `unclassified/` 原图；`candidate_manifest.csv` 记录候选路径、原图路径、一级/二级簇、来源局、帧号和格子。

候选生成仍然不判断英雄或星级。标注者只需确认每个最内层候选目录是否同英雄同星级或同一种空格状态：一致时可批量移动其中 PNG；混合时分别移动。候选一致不能作为原簇全部图片一致的数学证明，发现异常时仍可回到对应 `unclassified/` 一级簇补查。

当前命令默认使用 `datasets/hero_classifier/` 作为数据根目录。仓库通过 `.gitignore` 排除整个 `datasets/`，避免真实游戏截图和人工标签被提交。

数据根目录下的第一层按主 C 分组，例如 `assault/`。英雄标签目录仍按本局实际携带英雄扩展，不要求提前创建不存在的英雄类别。这样其他英雄图片可以按需复制或整理到不同主 C 数据组中共用，而每组训练和评估仍可明确追溯到目标主 C。

用于分类器训练的完整截图必须保存在对应对局目录的 `raw/` 中，不得混入通用调试截图目录：

```text
datasets/hero_classifier/<主C>/<分辨率>/<角色>/rounds/<YYYYMMDDHHMM>/raw/
```

完整截图命名格式：

```text
{对局开始时间:YYYYMMDDHHMM}_frame{截图序号:06d}.png
```

裁剪图保存在 `<split>/imports/<import_id>/unclassified/` 中，命名格式：

```text
{对局开始时间:YYYYMMDDHHMM}_frame{截图序号:06d}_{格子标签}.png
```

示例：

```text
raw/202608111914_frame000123.png
unclassified/202608111914_frame000123_4B.png
```

含义：2026 年 8 月 11 日 19:14 开始的对局、第 123 张完整截图、棋盘第 4 行 B 列。棋盘只有 3 列、6 行，文件名不再重复记录主 C、角色和分辨率；三者由上级目录表达。

通用诊断命令 `wlxq-bot screenshot` 产生的单张截图仍保存在 `screenshots/raw/`。它没有主 C、角色和对局上下文，只用于人工检查或离线诊断，不应直接作为分类器训练数据。

`manifest.csv` 至少记录：

- `round_id`
- `main_c`
- `frame_index`
- `captured_at`
- `display_resolution`
- `client_width` / `client_height`
- `dpi`
- `role`
- `cell_label`
- `source_screenshot`
- `crop_path`
- `hero_label`
- `star_label`
- `sample_kind`：`hero`、`empty_plain`、`empty_effect`、`unavailable_plain`、`unavailable_effect` 或 `unknown`

人工通过移动目录完成分类后，`sync-labels` 完整扫描集中 `labeled/` 并原子重建 `dataset_manifest.csv`，标注者不编辑 CSV。新局只创建新 import，旧 import 和已分类数据保持不变。

## 人工标注约定

一个 import 裁切完成后，标注者处理该批 `unclassified/` 中已经聚类的单格图片，并移动到当前 split 共用的 `labeled/`：

- 英雄和星级能够可靠确认时，直接移动到 `labeled/<英雄>/star<N>/`。
- 被强袭或其他单位部分遮挡，但英雄和星级仍能可靠确认时，也放入同一个 `labeled/<英雄>/star<N>/`；标签属于该格真实英雄，不能标成遮挡它的单位。
- 普通空格移动到 `labeled/empty/plain/`。
- 英雄格为空，但有技能、弹道、光效或其他画面元素经过时，移动到 `labeled/empty/effect/`。
- 该逻辑位置尚未开放时，按是否有明显特效分别移动到 `labeled/unavailable/plain/` 或 `labeled/unavailable/effect/`，不得当作已开放空格。
- 遮挡严重、英雄或星级无法可靠判断时，移动到 `labeled/unknown/`。
- 不为了凑类别而猜测；`unknown` 不作为普通分类类别训练，只按整局隔离用于拒绝阈值调整和独立测试。

普通空格和未开放位置数量通常最多，可以减少其训练采样权重，但不应全部删除。`empty/effect` 与 `unavailable/effect` 是避免特效误报英雄的重要困难负样本，应保留。标签可靠的遮挡英雄直接进入对应英雄星级类别，无法确认的帧不能用来凑数量，应放入 `unknown`。

## 重复帧处理

第一版不删除重复或相似裁剪图。自动聚类只整理 `unclassified/` 的目录结构，帮助标注者从数千张图片中快速挑选，不等于去重或自动贴标签。保留全部图片的原因如下：

- 相邻帧可能包含不同朝向、动作阶段、遮挡程度和技能效果，对分类器有实际价值。
- 保留原始裁剪便于后续调整采样策略，不需要重新从完整截图生成。
- 去重不是标注者的责任，不能为了数据清理增加人工负担。

大量近似图片仍可能让长期停留的英雄、星级或普通空格获得过高权重。该问题在训练数据加载阶段解决，而不是破坏性删除素材：

- 按实际用途为每个存在的类别分配业务权重：1 星和 2 星英雄为 `1.0`，主 C/其他英雄 3 星为 `0.8/0.5`，主 C/其他英雄 4 星为 `0.3/0.1`，`empty/unavailable` 为 `0.5/0.3`；不再让所有类别完全等权。
- 每个类别内部再按来源局均衡，避免某一局中长期停留的英雄获得过高权重。
- 同一类别和来源局内部再按现有样本类型均衡；普通/特效空格和普通/特效未开放位置分别控制期望组权重，避免数量最多的简单画面淹没困难样本。
- 对稀有英雄和星级提高抽取概率。
- 保留来源局数，避免模型只记住某一局、某一格或某一种背景。

## 数据集划分

禁止把同一局的相邻截图随机拆到训练集和测试集。训练、验证和测试必须按整局划分，例如：

```text
202608111914、202608112021 -> train
202608121903 -> validation
202608122010 -> test
```

同一局产生的完整截图和所有格子裁剪只能属于同一个集合。再次请求导入同一局时直接提示并跳过，不能重复裁切，也不能借重复请求把它转移到其他 split。测试局不能参与阈值选择、类别补样或模型微调。

跨分辨率验证时，目标分辨率至少保留若干完整对局作为未参与训练的独立测试集。模型运行前仍需把不同物理尺寸的格子裁剪统一缩放到固定输入尺寸，例如 `96×96` 或 `128×128`；是否支持某个分辨率必须由该分辨率的真实测试集确认。

## 最小验证范围

首次实验不要求立即采满全部英雄和星级：

1. 先用 1 局验证 12 格自动裁剪、目录分类和数据清单是否正确；该局可以重新纳入后续划分，但重新裁剪时不得混用旧坐标产物。
2. 最小可行性验证使用 4 局且只选择一个主 C：2 局训练、1 局验证、1 局独立测试。为减少首轮标注量，可以先按每 2 秒 1 张采集。
3. 4 局只能判断技术路线是否值得继续；关键英雄和星级没有同时覆盖训练、验证和测试时应补打 1～2 局。如果根据测试局调整模型、阈值或补样，必须另采新的独立测试局。
4. 路线可行后扩展到约 10 局；建议 6 局训练、2 局验证、2 局测试。
5. 每个准备声明支持的类别都应在多个独立对局中出现；没有真实测试素材的类别保持未支持。

最低验证不能只看总体准确率，因为普通空格可能掩盖英雄类别错误。至少单独检查：

- 不同英雄之间的混淆。
- 1 星与 2 星之间的混淆。
- 其他英雄被误报为 2 星及以上主 C。
- `empty/effect` 被误报为英雄。
- `unavailable` 被误报为已开放空格或英雄。
- 部分遮挡英雄被误报为实施遮挡的强袭或其他单位。
- 低置信度或类别冲突能否被拒绝为 `unknown`。

## 命令与代码位置

该能力使用明确的 `hero-classifier` 命令组，不复用 `debug`、`dataset`、`training` 等容易与其他功能混淆的泛化名称：

```text
wlxq-bot hero-classifier collect   # 固定时间点采集完整客户区截图
wlxq-bot hero-classifier import-rounds # 指定多局创建 split import，集中裁切并联合聚类
wlxq-bot hero-classifier select-candidates # 为历史 import 补生成少量人工候选图
wlxq-bot hero-classifier suggest-labels # 用已训练 ONNX 对新 import 的 candidates 离线预分类
wlxq-bot hero-classifier sync-labels   # 扫描人工标签并完整重建数据清单
wlxq-bot hero-classifier crop      # 单局排查和旧数据兼容
wlxq-bot hero-classifier group     # 单独检查聚类效果
wlxq-bot hero-classifier train     # 按整局隔离训练并导出 ONNX
wlxq-bot hero-classifier evaluate  # 使用未参与训练的整局数据评估
```

代码按功能收口：

```text
src/wlxq_bot/hero_classifier/
  collector.py
  cropper.py
  dataset.py
  grouper.py
  labels.py
  suggester.py
  trainer.py
  evaluator.py

src/wlxq_bot/perception/hero_classifier.py  # 正式运行时 ONNX 推理适配
```

训练依赖通过 `pip install -e ".[train]"` 单独安装。正式运行与 ONNX 评估复用现有 OpenCV DNN，不要求安装 PyTorch。
